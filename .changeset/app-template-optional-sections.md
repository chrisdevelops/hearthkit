The template now carries a conditional section for each optional hearthkit package — `storage`, `email`, `auth` and `payments` — plus one Playwright flow per package. This is the outstanding half of Phase 5's definition of done: the gates half was met when `payments` merged, and this is the "template's conditional sections render for each" half, which previously had no coverage at all.

The template is the superset and pruning is subtractive, per plan sections 5 and 4.10. One declared map, `appTemplateSectionsByOptionalPackage`, says which paths and environment variables each optional package owns. `create` consumes that map in Phase 6; nothing is generated or assembled at scaffold time.

**Whole-file pruning is not sufficient, and that changed the mechanism.** `app-runtime-config.ts` composes `appEnvSchemaFragments` from named imports, so selecting `storage` means adding an import to a file that exists in every project. The same is true of `app-health-checks.ts` and `transpilePackages`. Pruning a file cannot remove an import from a file that survives. So marked blocks are now deleted from source, narrowed to deletion between balanced markers — no value is rewritten, no identifier substituted, no placeholder filled. The Phase 4 line that said "it never string-substitutes source" is amended in place rather than left contradicted; the prohibition it guarded is unchanged.

An **absent** selection returns text unchanged, because that is the template itself and it must keep its markers to stay prunable. An **explicit** selection deletes unselected blocks and strips the marker lines of kept ones, so a generated project contains no marker text. Confusing the two silently produces the wrong tree.

`isPrunedTemplatePath` is replaced by `decideTemplatePathPrune`, which returns a union naming the package that caused a deletion rather than a boolean — the second question the old signature could not express, and the one `create` needs. An `is…` returning a record was a lie, so the name went with it.

**Fixes an unrelated bug found while verifying:** `next.config.ts` sets `output: 'standalone'`, but `start` was `next start`, which Next warns is unsupported — and the two serve different artifacts, so local and container did not behave the same. `start` now runs `start-standalone-server.ts`, which locates the emitted server, copies `public/` and `.next/static` beside it, and spawns it. The literal `node .next/standalone/server.js` was rejected on measurement: Next roots tracing at the workspace, so the server sits at `.next/standalone/templates/app/server.js` here and at the root in a generated project. A hardcoded path passes in a generated project and fails exactly where the flows run.

**Verification.** 58 Vitest gates, all offline. Six Playwright tests: the two always-on smoke tests plus one flow per optional package, run against real Postgres, real MinIO, an isolated Mailpit and Stripe test mode. The payments flow never automates Stripe's hosted UI — it asserts the redirect carries the right session, then posts a signed `checkout.session.completed` and asserts the purchase row. `verify:container` passes all seven steps against an empty-selection materialization.

Notes for anyone extending this. `export const dynamic = 'force-dynamic'` is inert on Client Components — Next's own source says only server components carry segment configuration — so it takes effect on `/billing` and nowhere else. `db:generate` needs all ten tables re-exported individually, because drizzle-kit only inspects a module's top-level exported values and cannot see a table nested inside a schema object; without that the migration comes out empty. The template's flows need their own Mailpit: `packages/email`'s gates clear that container wholesale and assert exact message counts, so a shared one breaks in both directions. `@types/pg` is deliberately not declared here — it has no owner in the section map, so `create` would never prune it and every minimal project would install it for nothing.
